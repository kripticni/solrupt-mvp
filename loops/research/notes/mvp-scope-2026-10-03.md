- **F3 — PROVE window** (identity + finding + proof + profile).
  - F3.1 Nickname sign-in: claim-a-name (unique per event) + session UUID in localStorage; optional wallet-pubkey string; guest mode allowed (marked guest). No passwords/OAuth/email.
  - F3.2 Finding form: severity select (Critical/High/Medium/Low) + proof (what the exploit did, 2–3 sentences) + fix (1–2 sentences); required before proof issues.
  - F3.3 Public proof page (no login to view): solver hash, timestamps, attempts + hints used + time spent, code digest, verifier version pin, re-run recipe, blind-grade status. Bar: stranger re-verifies alone (the honest-test procedure).
  - F3.4 Profile merged into proof page: lessons done, rooms solved, rating, next-step panel (3–4 static curated links: First Flights, Earn, Immunefi/Cantina Solana filters — existing opportunities only, never a job board).

## 4b. Platform prerequisites (build first, in this order)

- P0.1 Toolchain pins: Rust + LiteSVM + Anchor versions pinned, Cargo.lock committed, L1 `.so` prebuilt with digest BEFORE any UI work.
- P0.2 SQLite schema: `users(nickname UNIQUE, wallet NULL, created)` · `sessions(uuid, user, room, created, expires, reaped)` · `attempts(session, code_hash, verdict, at)` · `hints_used(session, hint_n)` · `solves(user, room, points, first_at)` · `findings(user, room, severity, proof, fix, solver_hash, at)`.
- P0.3 Session handling: UUID per Run, fresh keypairs/program IDs per session, 900s TTL + reaper sweeper, per-IP caps, localhost-bound, flag/solver never leaves server.
- P0.4 API skeleton: `POST /run` (exploit → verdict) · `POST /finding` → issues proof · `GET /proof/:hash` (public) · `GET /board` · `GET /rooms` · static frontend. One small server, no framework ceremony.

- P0.6 Evidence logger: append-only rows from 11:00 Sat (hypothesis → test → result, exact commands + outputs, failures verbatim) — feeds Sunday's README.
- P0.7 Sunday prep built Saturday: offline fallback bundle (frozen transcript + local LiteSVM run, no net) + recorded offline demo + production site live for judges/users + `VENDOR_NOTICES` + AI disclosure draft.
- P0.8 Deck + pitch: 3 core slides (Problem+result / Demo flow / Impact-next test) + 4+3+1 rehearsal Sunday 11:00–13:00.
- P0.9 Production site live (Sunday-critical path, not a footnote): static frontend + one API process + SQLite file on a reachable host; public URL printed in deck + QR (target: Sun 10:00, before 11:00 freeze); `/health` endpoint green; venue demo runs against RECORDED video first, live site second; fallback = same bundle served from team laptop over hotspot if venue net/host dies. Deploy Saturday evening if humanly possible — Sunday morning is for evidence, not DevOps.
- P0.10 Database (locked): the SQLite file from P0.2 IS the production database — it lives next to the API process, no DB server, no Postgres, no migrations ceremony (back up by copying the file).
